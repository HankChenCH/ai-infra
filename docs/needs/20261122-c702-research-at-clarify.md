# 调研归位：系统调研在澄清阶段串 dev-research，退出实现管道

## 背景与业务目标

用户反馈（2026-11-22）：需求开票使用调研驱动时拆出的调研票，被 dev-execute 按
dev-implement 纪律执行而非 research 纪律，调研结论失真；且调研票出现在实现流程，
违背「调研先于设计」的脊柱次序（docs/METHOD.md:108：clarify → 调研（research）→
设计（spec / design / prototype）→ 规划 → 实现）。

根因（查证 2026-11-22，逐条有出处）：

1. dev-clarify 出口三路归置规则「转调研不许悬置：变 FR（调研报告是交付物）」
   （docs/sdlc-skills-blueprint.md §11.13、skills/dev-clarify/references/research.md
   落盘映射节）把研究问题送进 spec → 票 → implement 管道。先例：need 0001 FR-2
   （tracker 平台调研报告作为 FR）。
2. 执行端无识别：dev-plan 拆票「type 一律 feature」（skills/dev-plan/SKILL.md:72，
   无 research 票型）；dev-execute 全票派实现子代理执行 dev-implement 纪律全文
   （skills/dev-execute/SKILL.md §5.1，无按交付物路由的分叉）。
3. dev-research 的全部调研纪律（后台代理并行检索、只信一手来源、每条结论带引用与
   检索日期、防编造、检索不可用停手）在实现管道中不生效。调研票被 implement 纪律
   生产，产出是训练记忆 + 顺手检索冒充的调研结论，验收标准照常打勾——失真机制性成立。
4. dev-research 定位「按需服务不进自动串联链」（蓝图 v1.11 修订记录），与 dev-clarify
   调研驱动的「联动触发」只有触发面描述（蓝图 §11.14 触发行），联动时序从未定义。

业务目标：调研结论只出自 dev-research 纪律；实现管道只出现实现票。可验证目标：

- 调研驱动产生的研究问题不再变成任何工单（docs/tickets/ 零新增调研交付物票）；
- spec 的实现决策引用盘上调研报告（docs/research/ 带 need 谱系前缀）作为依据；
- 纯调研需求（报告即全部交付物，先例 need 20261110-a98b 的 round 1）不经
  spec / 票 / 运行管道即达 need 终态；实现前调研（调研为实现选型服务）的 need
  照常经管道，报告只作 spec 输入，调研部分不产生工单。

不做的代价：选型与依赖判断继续建立在无来源结论上，错选型的返工随实现规模放大；
调研产物可信度靠人盯来源维持（need 0001 FR-2 当年即人工盯出，机制不保真）。

## 干系人与用户

- **需求提出者（用户）**：在 clarify 内得到「已调研清楚」的 need。成功标准：need
  定稿时开放问题无悬置调研；每条开放问题指得回报告结论、假设或非目标。
- **spec 作者（dev-spec 会话）**：开工时有可引用的调研报告。成功标准：实现决策与
  测试决策条条指得回报告编号或 need 拍板记录。
- **实现编排者（dev-execute 会话）**：名下票全是实现票。成功标准：无一张票的
  验收标准是「报告落盘」类条目。
- **纯调研需求提出者**：以报告为终态交付物（报告后无实现交付物）。成功标准：
  need 置 fulfilled 凭报告落盘 + 用户通读拍板，全程无票无 spec。

## 系统能力需求

溯源约定：FR-1、FR-2、FR-3、FR-4 均指回用户原话与拍板（2026-11-22「按你建议」
+ D3 分情况拍板 + D4 定稿拍板）。

- **FR-1 澄清就地联动调研**：dev-clarify 调研驱动遇到系统调研级问题（多来源、
  要引用、要对比，内联查证兜不住）时，就地触发 dev-research：规整研究问题三要素
  → 问题清单经用户确认 → 检索出报告 → 结论回填 need（事实进正文对应节、方向
  取舍走决策卡）→ 之后才进入定稿。（用户原话：「我期望的是在需求澄清触发调研
  驱动是来调用 research 而不是实现阶段」）
- **FR-2 逃生舱退役**：三路归置规则中「变 FR（调研报告是交付物）」路径废止；
  调研报告只作 need 正文依据与 spec 输入，永不成为工单。用户拒绝联动或
  dev-research 不可用 → 该问题过查证过滤闸转假设，假设条目显式标注「未经系统
  调研」。dev-plan / dev-execute / dev-review / check.sh 零改动（管道里天然
  只剩实现票）。
- **FR-3 调研分两态归置**：判据 = 报告之后是否还有实现交付物。实现前调研（报告
  为实现选型服务）：need 照常经 spec / 票 / 运行管道，报告只作 spec 输入依据，
  调研部分不产生工单，终态走常规验收收口；纯调研（报告即全部交付物，形态先例
  need 20261110-a98b round 1）：不经 spec / 票 / 运行管道，need 确认后由
  dev-research 交付报告（可按主题多张，文件名带 need 谱系前缀），用户通读拍板后
  need 置 fulfilled（记账留痕，先例提交 cc73c11 的 [trivial] need 置终态形态）。
  - 勘误（2026-11-24，验收 20261124-a369 折回）：所引先例提交 `cc73c11` 经 git 核验
    为 pre-push 修复提交（票 20261122-e00b），不是 need 置终态提交；need 置
    fulfilled 的 [trivial] 记账形态先例为 `7aaaee2`、`f16c115`、`6a034d2`。原文
    保留不回改，以本条为准。
- **FR-4 缺报告显式提示**：dev-spec 起草实现决策时，若依据的是假设表中带「未经
  系统调研」标注的条目，向用户显式提示该风险（提示不拦截——报告是思考工具不是
  流程税，沿用 dev-research 值得做亮牌的同款价值取向）。

## 场景

- **主流程一（调研问题模式）**：Given clarify 用调研驱动且出现系统调研级问题，
  When 三要素规整并经问题清单确认，Then 就地调 dev-research，报告落盘（docs/
  research/ 带 need 谱系前缀）后结论回填 need，开放问题清零，need 定稿；后续
  dev-spec 起草实现决策时引用报告编号。
- **异常流一（用户拒绝联动）**：Given 系统调研级问题但用户拒绝联动调研，When 过
  查证过滤闸，Then 该问题转假设并标注「未经系统调研」，need 可定稿；spec 起草时
  该标注被显式提示（FR-4）。
- **异常流二（dev-research 不可用）**：Given dev-research 技能未安装或检索工具
  不可用，When 如实相告，Then 走异常流一同款转假设路径，不以内联查证结论冒充
  系统调研结论（research.md 诚实边界条款保留并强化）。
- **主流程二（纯调研需求）**：Given 报告即 need 的全部交付物（报告后无实现
  交付物），When need 确认，Then dev-research 交付报告，用户通读拍板后 need 置
  fulfilled；全程无票无 spec、不建 worktree 不进运行。
- **对照场景（实现前调研）**：Given 报告为实现选型服务（报告后还有实现交付物），
  Then 走主流程一（或确认后手动触发 dev-research），报告落盘后 need 照常进
  spec / 票 / 运行管道，报告被 spec 实现决策引用，不产生调研工单。
- **异常流三（调研否掉方案）**：Given 调研结论否掉某候选方案，Then 该方案进 need
  「范围与非目标」（research.md 落盘映射既有条款，保留不变）。
