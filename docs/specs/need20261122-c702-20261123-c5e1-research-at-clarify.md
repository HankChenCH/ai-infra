# 调研归位 round 1：澄清就地联动 dev-research、逃生舱退役、调研分两态归置

## 问题陈述

需求澄清用调研驱动时，要系统调研的研究问题经三路归置逃生舱「变 FR（调研报告是
交付物）」流进 spec → 票 → 实现管道，被 dev-implement 纪律（红绿循环）执行——
dev-research 的调研纪律（一手来源、引用与检索日期、防编造）全程不生效，产出的
"调研结论"是训练记忆冒充的，且实现管道里出现了本不该存在的调研票（need
20261122-c702 问题陈述）。联动触发只有触发面描述，时序从未定义，报告没有机会
先于 spec 落盘。

## 方案

把 dev-research 与 dev-clarify 调研驱动的联动补上明确时序：系统调研级问题在
澄清会话内就地触发 dev-research（问题清单确认 → 检索出报告 → 结论回填 need），
报告落盘回填后才许定稿；三路归置逃生舱「变 FR（调研报告是交付物）」退役，调研
报告永不成为工单。调研归置分两态（判据 = 报告后是否还有实现交付物）：实现前
调研照常经 spec / 票 / 运行管道，报告只作 spec 输入；纯调研需求（报告即全部
交付物）不经 spec，报告交付 + 用户通读拍板后 need 置 fulfilled。dev-plan /
dev-execute / dev-review / check.sh 零改动——管道里天然只剩实现票。改动全部是
文档与技能语义（蓝图三处 + dev-clarify / dev-research / dev-spec / GLOSSARY），
配静态锚定断言防回退。

本轮范围（分轮提议，待用户确认）：need 20261122-c702 全量 FR-1…FR-4。四条 FR
同属一次归位改造，拆轮无收益；need R1（存量文案同步）恰要求蓝图与技能同批改完
防旧逃生舱引用死链，同批即最小可交付范围。

## 用户故事

1. 作为需求提出者，我想要系统调研级问题在澄清会话内就地触发 dev-research，以便
   need 定稿时结论已有一手来源背书，而不是悬到实现阶段。
2. 作为需求提出者，我想要拒绝联动时问题转假设并标注「未经系统调研」，以便定稿
   不被调研卡死，风险仍诚实可见。
3. 作为 spec 作者，我想要实现决策能引用盘上调研报告，以便选型依据条条指得回
   一手来源。
4. 作为实现编排者，我想要名下票全是实现票，以便红绿循环与评审契约不再作用于
   调研交付物。
5. 作为纯调研需求提出者，我想要报告交付并通读拍板后 need 直达 fulfilled，以便
   不为一份报告走 worktree / 评审 / 合并全套实现机器。
6. 作为 spec 作者，我想要依据「未经系统调研」标注的假设起草时被显式提示，以便
   不静默继承未核销风险。
