# 调研驱动：内联查证与系统调研的分工

dev-clarify 开场亮牌选中本方法后加载。适用：技术/外部依赖不确定。
核心动作：把每一条"我不知道"分层处置——多数在对话里查掉，少数才值得立项调研。

## 分工三层

| 层级 | 谁干 | 产物去向 |
|---|---|---|
| 内联查证（秒~分钟级、单来源） | 本技能当场查（读码/读文档/搜一下） | 结论 + 来源链接直接进对话或 need 正文 |
| 系统调研（多来源、要引用、要对比） | dev-research | 就地触发 dev-research，报告回填 need（研究问题按三要素记进 need） |
| 事实核验（"某 API 支不支持 X"） | 查证过滤闸 | 查完变事实；查不了才转假设 |

## 研究问题三要素（记进 need 的格式）

每条一行：**要回答什么 / 为什么重要（堵着哪个决策）/ 影响哪个 FR 或假设**。

- 好：`GitLab 凭据验证走 glab auth status 是否可靠？——决定 FR-1 的验证方式，
  选错则回落逻辑白写。`
- 坏："需要调研 GitLab。"——三要素缺全，是焦虑不是问题。

## 就地联动时序（系统调研级问题不悬置、不变成工单）

系统调研级问题（多来源、要引用、要对比，内联查证兜不住）由本技能就地联动 dev-research，
时序：研究问题三要素规整 → 问题清单经用户确认 → 检索出报告 → 结论回填 need → 之后才定稿。
报告作 need 正文依据与 spec 输入，不产生工单。
用户拒绝联动或 dev-research 不可用 → 过查证过滤闸转假设，条目标注「未经系统调研」。

## 诚实边界

- dev-research 未安装 → 如实相告："深度调研要等 dev-research 或你自己
  来"；本技能可做轻量内联查证，但结论必须标注"内联查证，未做系统调研"，
  不得冒充调研结论。
- 只信一手来源（官方文档、代码本身）；二手结论标注来源与检索日期。
- 查证不能替用户拍板：查到的事实进 FR/范围，方向取舍仍走决策卡。

## 好/坏对照

- 好："官方文档写明支持（链接，2026-10-27 检索）→ FR-2 可以这么写。"
  ——事实带出处进了产物。
- 坏："网上都这么做。"——无来源，落盘即负债。

## 落盘映射

查到的事实 → 正文对应节（注明来源与日期）；研究问题 → 开放问题（三要素），
清零时按三路归置——转调研 = 就地联动 dev-research，报告落盘后按结论去向归置：
报告答掉的 → 正文对应节（结论回填 need）；方向取舍 → 决策卡；
调研明确否掉的方案 → 范围与非目标。
用户拒绝联动或 dev-research 不可用 → 过查证过滤闸转假设，条目标注「未经系统调研」。

## 自查口令

每条"不知道"分层了吗（当场查掉 / 记三要素 / 转假设）？研究问题三要素齐吗？
有没有把内联查证的结论当系统调研的结论用？
